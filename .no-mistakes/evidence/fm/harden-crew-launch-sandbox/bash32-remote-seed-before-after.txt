Pre-existing bash 3.2 empty-array crash in the remote seed - before/after
branch fm/harden-crew-launch-sandbox, target commit 5d8bcab
Captured 2026-08-31T22:50:31Z on Darwin 27.0.0 (arm64), GNU bash, version 3.2.57(1)-release (arm64-apple-darwin26)

bin/fm-remote-home-seed.sh expanded "${PROJECT_NAMES[@]}" on an empty array
under `set -u`. Stock macOS bash 3.2 rejects that as an unbound variable, so
every --no-projects seed died at that line before doing any work. The defect is
independent of this branch's launch hardening; it is fixed here only because the
branch's new remote secondmate coverage cannot run on macOS without it.

Both runs below drive the real bin/fm-remote-home-seed.sh with an identical
stub ssh that answers the readiness probe and refuses the dispatch that follows,
so the only difference between them is the one-line array expansion. Paths are
scrubbed to <repo> and <tmp>.


########## BEFORE (bin/fm-remote-home-seed.sh at 8e6b1f9, the fix's parent) ##########

$ bash --version -> GNU bash, version 3.2.57(1)-release (arm64-apple-darwin26)
$ fm-remote-home-seed.sh probe remote-mac /srv/fm-root /srv/fm-home --no-projects
<repo>/bin/fm-remote-home-seed.sh: line 190: PROJECT_NAMES[@]: unbound variable
  exit=0

  The seed never reached the remote host, and worse, it reported exit 0: in
  bash 3.2 the EXIT trap's own final status replaces the failing status, so the
  crash surfaced to the operator as a silent success that provisioned nothing.
  Measured separately with the status captured directly:

    $ FM_HOME=<tmp>/home ... fm-remote-home-seed.sh probe remote-mac /srv/fm-root /srv/fm-home --no-projects

    BEFORE_EXIT=0

  The project loop is now skipped for a project-less seed, the run continues to
  the first real remote step, and the failure it hits there is reported honestly
  with exit 1 instead of being masked.
